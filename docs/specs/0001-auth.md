# 0001 · Auth sessions and route protection

**Status**: In Progress
**Date**: 2026-10-17

## Summary

Use InsForge's official SSR helpers with cookies on the app origin. OAuth starts and completes on the server. Next.js Proxy refreshes sessions before rendering, and protected pages verify identity with InsForge.

## Context

Feature 02 in context/build-plan.md requires Google and GitHub login, session management, protected app routes, and a dashboard redirect. The current app has only the homepage. The user authorized establishing the approach and implementing it using existing conventions.

## Decision

Use `@insforge/sdk/ssr` (SDK 1.5.2) rather than the obsolete `@insforge/ssr` examples in library-docs.md. Keep `lib/insforge-client.ts` and `lib/insforge-server.ts` separate. Use `getCurrentUser()`, not the obsolete `getUser()` example. Current MCP and official SDK documentation take precedence per library-docs.md.

Start OAuth in `actions/auth.ts`, restricting providers to google/github. Persist the PKCE verifier in a ten minute httpOnly, SameSite=Lax cookie. Complete OAuth in `/api/auth/callback`, where cookies can be written. This replaces the planned callback page because Server Components cannot write cookies. Exchange only when both code and verifier exist, clear the verifier on success or failure, and redirect to a fixed `/dashboard` destination. Errors return to `/login` with a generic error code, never raw provider text.

The SDK owns cookie names and JWT expiry. Refresh cookies remain httpOnly. Access cookies follow the SDK's browser-readable default for future Storage/Realtime. Both use Secure in production and SameSite=Lax. Tokens are never returned from Server Actions.

`proxy.ts` uses `updateSession` and forwards refreshed request cookies before Server Components render. It redirects anonymous visitors away from `/dashboard`, `/profile`, and `/find-jobs` including descendants. Cookie presence is only an early check: each protected page calls `requireUser()`, which verifies with InsForge. Future Server Actions and API routes must verify independently before reading user data.

The refresh POST route enforces same origin and delegates cookie rotation to the SDK. Logout is a Server Action, clearing cookies and refreshing navigation. Auth pages and session responses are not publicly cached. The homepage stays public; its CTA destinations reflect the verified session.

| Callback origin | APP_URL, validated configured origin, never request host |
| OAuth provider | Validated form value, google or github |
| Verifier and authorization URL | InsForge signInWithOAuth response |
| Callback code | insforge_code query parameter |
| Session cookies | InsForge exchange/refresh results through SDK helpers |
| Identity and displayed email | InsForge getCurrentUser response |
| Destination | Fixed /dashboard after login, /login after logout |
| Page titles and empty states | Build plan's deferred page features |

## Options and consequences

Browser-only OAuth is simpler but does not establish app-owned server cookies for route protection. Official SSR helpers fit the existing architecture and centralize token rotation. The tradeoffs are request-time user verification and a short-lived browser-readable access token. A fully httpOnly access token would require proxying future browser SDK operations and is unnecessary for the documented project model.
